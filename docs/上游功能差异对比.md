# 与上游 MihoyoBBSTools 的功能差异

> 对比时间：2026-11-21
>
> 上游：`D:\GitHub\Womsxd\MihoyoBBSTools`，HEAD `01be3ba`（2026-11-01，米游社客户端 `2.117.0`）
>
> 本项目：`D:\GitHub\bcmdy\mihoyo-bbs-tools-rs`，HEAD `e7db422`（米游社客户端 `2.117.0`）
>
> 口径：只比较用户可感知的功能与运行方式；不比较实现语言、代码质量和上游疑似缺陷。结论来自双方源码、配置示例和文档的静态对照，未对上游做运行验证。

## 1. 结论

核心自动化能力已经对齐：国服 6 款游戏、HoYoLAB 5 款游戏、3 项云游戏、米游社 9 个板块的社区任务、米游币任务判定、多账号、凭据刷新、青龙、DaCapo、旧配置迁移、常驻调度都有对应实现；验证码、代理、复查重试、报告、诊断和安全处理还强于上游。

真正需要决策的缺口集中在三块：

1. **通知**：缺 `qbot`（QQ 官方机器人单聊）渠道；SMTP 只有纯文本，没有上游的 HTML 模板与随机背景图。
2. **部署与分发**：Docker 镜像没有上游的容器内定时（`CRON_SIGNIN`/`MULTI`）和 `docker-compose.yml`；Nix 只有 package，没有上游的 Home Manager 模块；没有 macOS 构建。
3. **迁移兼容**：旧 `push.ini` 不自动转换；`logging.ini` 自定义日志、自定义 UA 自动补版本号、Bark 预设图标等细节未对齐。

其余差异多为实现模型不同或本项目主动取舍，不构成功能缺失。

## 2. 缺口逐项说明

### 2.1 `qbot` 推送渠道（P1）

- 上游：`push.py:163-199` 实现 QQ 官方机器人单聊推送；先用 `appId`/`clientSecret` 调 `POST https://api.bot.qq.com/app/getAppAccessToken`，再带 `Authorization: QQBot <access_token>` 调 `POST /v2/users/{openid}/messages`，消息体 `{content, msg_type:0}`；配置示例在 `config/push.ini.example:27-33`，说明在 `config/README.md:98-119`。该渠道是 2026-10-30 新增的。
- 本项目：`src/config/mod.rs:497-725` 的 `NotificationProvider` 共 20 种，`src/push/mod.rs:49-121` 的 `ProviderKind` 对应 20 种；全仓库没有 `qbot`、`getAppAccessToken` 或单聊 OpenID 相关代码。
- 影响：只影响使用 QQ 官方机器人单聊的用户；其它 20 个渠道不受影响。上游的 qbot 是主动消息，还受“允许主动发送”开关限制。
- 建议：实现 `qbot` 渠道（`appid`/`secret`/`openid`，可选 `api_url` 便于测试），并像其它渠道一样接入 `notification list/test`、配置向导和文档。openid 获取工具见 2.6，可后置。
- 预估：5–7 小时。

### 2.2 `push.ini` 配置迁移（P1）

- 上游：通知完全由 `config/push.ini` 承载，支持 `AutoMihoyoBBS_push_path` / `AutoMihoyoBBS_push_name` 指定路径（`push.py:34-58`），`push_server` 还支持逗号分隔多服务（`push.py:526-559`）。
- 本项目：通知写在 YAML 的 `notifications` 节点；旧 v11–v15 配置迁移时会显式丢弃 `push` 字段并告警“旧版 push.ini 文件引用无法转换为内联通知配置，未迁移”（`src/config/legacy.rs:237-242`）。
- 影响：从 Python 版迁移的用户必须手工把推送段改写成 `notifications.providers[]`，否则不会收到任何通知，且只有一条警告。
- 建议：新增 `migrate-push`（或并入 `migrate-config`）读取 `push.ini`，把 `push_server`、`push_token`、`block_keys`、`error_push_only`、各渠道段映射为 `NotificationProvider`；多服务逗号写法可拆成多个 provider。无法映射的字段输出明确清单。
- 预估：2–3 小时。

### 2.3 SMTP HTML 邮件与随机背景图（P2）

- 上游：`push.py:202-249` 读取 `assets/email_example.html` 模板，把标题、正文、背景图渲染成 HTML 邮件；背景图来自 `https://www.loliapi.com/acg/pc/`，`[smtp] background` 可关闭；`push.ini.example:84-100` 给出完整字段。
- 本项目：`src/push/smtp.rs:65-69` 用 lettre 发送纯文本，正文是 `标题 + 两行换行 + 报告`；`smtp` 没有 `background`、`html` 之类的字段。
- 影响：只影响邮件观感，不影响送达；偏好 HTML 邮件的用户会觉得功能缩水。
- 建议：若要做，建议内置一个精简 HTML 模板，背景图做成可选开关且默认关闭，避免依赖第三方随机图 API；同时保留纯文本回退。
- 预估：1–2 小时。

### 2.4 容器内定时、compose 与 Docker Hub（P2）

- 上游：`docker.py:17-50` 在容器内按 `CRON_SIGNIN`（默认 `30 9 * * *`）循环执行，`MULTI=TRUE` 时走多配置；`Dockerfile:3-5,17` 设置默认环境变量并以 `docker.py` 为 `CMD`；根目录有 `docker-compose.yml`（`restart: always`）；镜像同时发布 Docker Hub 与 GHCR（`.github/workflows/docker-buildx.yml:57-65`）。
- 本项目：`Dockerfile:37-38` 是 `ENTRYPOINT ["MihoyoBBSToolsRS"]` + `CMD ["run"]`，即一次性执行；没有 `docker-compose.yml`，全仓库没有 `CRON_SIGNIN`/`MULTI` 处理；容器 workflow 只发布 GHCR（`.github/workflows/container.yml:63,109`），文档也只给 `docker run`（`docs/使用说明.md:1167-1186`）。
- 影响：从上游 compose 迁移的容器用户会发现“起容器后不会自动每天跑”；需要改命令行用 `schedule`，或另配 host cron。拉取习惯也需要从 Docker Hub 改为 GHCR。此外，上游任意入口都会读取 `AutoMihoyoBBS_config_path`/`AutoMihoyoBBS_config_prefix`，本项目只在 `qinglong` 子命令中读取同名变量，普通 `run` 需要用 `--config`，容器迁移时容易踩空。
- 建议：
  - 增加 `docker-compose.yml` 示例，默认 `command: ["schedule"]`；
  - 兼容 `CRON_SIGNIN`/`MULTI`（或至少在容器启动脚本里提示改用 `schedule`/`run-directory`）；
  - 如需照顾存量用户，可同时推送 Docker Hub（需要新增 secrets）。
- 预估：2–4 小时（含文档）；Docker Hub 发布另加 0.5 小时。

### 2.5 Nix Home Manager 模块（P2）

- 上游：`flake.nix:58-172` 提供 `homeModules.default`，包含 `services.mihoyo-bbs-tools.{enable,onCalendar,persistent,settings,extraEnvironments}`，生成 systemd user service 与 timer（`OnCalendar` + `RandomizedDelaySec = "20min"`）；README `README.md:314-410` 给出 Home Manager 示例，并说明 Linux 与 macOS 都可用。
- 本项目：`flake.nix:7-52` 只有 `packages`（`buildRustPackage`）和 `apps`，没有 `homeModules`/`nixosModules`；文档 `docs/使用说明.md:1148-1165` 只说明 `nix run`/`nix build`。
- 影响：Nix 用户需要自己写 systemd 单元或 cron，不能像上游一样声明式配置定时和配置内容。
- 建议：增加 `homeModules.default`，把 `settings` 渲染到 `~/.config/.../config.yaml`，生成 user service + timer；配置内容仍建议用 `runtime.schedule` 或外部 timer 二选一，避免双跑。
- 预估：2–4 小时。

### 2.6 `qbot` openid 获取工具（P3）

- 上游：`qbot_get_openid.py` 是完整的 363 行工具：内置最小 WebSocket 客户端（握手、帧解析、心跳、重连），用 `C2C_INTENT = 1<<25` 鉴权，监听 `C2C_MESSAGE_CREATE` 取 `author.user_openid`，并按原文件换行风格写回 `[qbot]` 段；支持 `--appid`/`--secret`/`--timeout`。
- 本项目：没有 WebSocket 客户端，也没有 openid 获取命令；CLI 里没有任何相关入口。
- 影响：即使实现了 qbot 渠道，用户仍需要从别处拿到 openid；上游用户会明显感到缺一步。
- 建议：
  - 短期：在文档中指引使用上游 `qbot_get_openid.py` 或其它工具获取 openid；
  - 长期：实现 `config qbot-openid`（推荐复用 reqwest 的 HTTP upgrade 自写最小帧，避免引入完整 WebSocket 生态；代理与平台根证书行为也能与现有请求保持一致）。这会引入 TLS/WS 细节，需真实机器人凭据验收。
- 预估：10–14 小时（含命令、配置写入、文档与测试；不含真实机器人联调时间）。

### 2.7 `server.py` 式常驻控制台（P3，可不做）

- 上游：`server.py:95-126,367-464` 提供常驻交互模式，支持 `stop/exit`、`reload`、`test`、`single`、`multi`、`mod 1|2`、`time N`、`show true/false`、`add 'cookie'`、`set user attr value`、`help`；README `README.md:169-193` 把它作为 screen 下的推荐运行方式。
- 本项目：`schedule` 每轮重新加载配置，`automation`/`create-launcher` 负责系统级定时，`config` 子命令负责离线改配置；没有运行中的交互控制台，也没有“按指令立即跑一次/切换单多用户”的能力。
- 影响：对习惯 screen + 控制台的用户是体验差异；对定时无人值守场景没有影响。
- 建议：不建议现在实现交互式 REPL。可以在文档中说明 `schedule` + `config` + `notification test` 的替代路径；如果确有需求，再单独设计。
- 预估：6–10 小时（价值低）。

### 2.8 `logging.ini` 自定义日志（P3）

- 上游：`loghelper.py:4-20` 在存在 `config/logging.ini` 时用 `logging.config.fileConfig` 完全接管日志；`config/logging.ini.example` 给出 formatter/handler/文件轮转示例。
- 本项目：`runtime.logging` 只有 `enabled`、`directory`、`file_prefix`（`src/config/mod.rs:164-187`），格式固定，按日滚动；级别可配，`RUST_LOG` 可覆盖。
- 影响：需要自定义日志格式、文件命名或多 handler 的用户无法直接迁移。
- 建议：优先级低；如需支持，提供少量格式化选项比引入通用日志配置更符合本项目风格。
- 预估：1–2 小时。

### 2.9 自定义 UA 自动补版本号（P3）

- 上游：`tools.py:138-152` 的 `get_useragent()` 会在用户自定义 UA 后面自动补 ` miHoYoBBS/{version}`；已经包含 `miHoYoBBS` 时只替换版本；`config.yaml.example:43-44` 的注释也说明“不要带版本号”。
- 本项目：`account.china_checkin.user_agent` 原样使用（`src/service/runner.rs:130`），默认值包含版本（`src/mihoyo.rs:39`），但自定义 UA 不会被追加或替换版本。
- 影响：从 Python 配置迁移的自定义 UA 可能与上游行为不同；多数自定义 UA 仍可用。
- 建议：在构造国内签到请求时，若 UA 不含 `miHoYoBBS/` 则追加当前版本；若含则替换为当前版本。注意不要影响 HoYoLAB 的独立 UA。
- 预估：0.5 小时。

### 2.10 Bark 预设图标名（P3）

- 上游：`push.py:350-361` 把 `icon=genshin` 等预设名拼成 jsdelivr 图标 URL；`push.ini.example:67-71` 列出 `genshin`、`mihoyobbs`、`honkai2`、`honkai3rd`、`tears_of_themis`。
- 本项目：`src/push/mod.rs:529-533` 把 `icon` 原样作为查询参数传给 Bark；`docs/使用说明.md` 把它描述为图标 URL。
- 影响：如果用户把上游的 `icon=genshin` 直接搬过来，Bark 不会显示预设图标。
- 建议：接受 URL 的同时兼容几个预设名，映射到与上游相同的图标地址。
- 预估：0.5 小时。

### 2.11 多用户交互确认与 `AutoMihoyoBBS_autorun`（P3）

- 上游：`main_multi.py:95-102` 非 autorun 时列出配置文件并等待回车；`main_multi.py:149` 支持 `AutoMihoyoBBS_autorun=1` 跳过确认。
- 本项目：`run-directory` 发现配置后直接执行（`src/main.rs:676-716`），没有确认步骤，也没有 `AutoMihoyoBBS_autorun`。
- 影响：对自动化是优点；对“怕误跑多份配置”的用户少一道保护。
- 建议：可加 `--yes`/`--no-confirm` 之类的显式开关，默认保持现在的非交互行为。
- 预估：0.5 小时。

### 2.12 macOS 官方构建（P3）

- 上游：Python 版可在 macOS 运行；README 的 Home Manager 说明也明确 Linux 与 macOS 都支持（`README.md:314-319`）。
- 本项目：发布矩阵只有 Linux x86_64/arm64/armv7 与 Windows x86_64（`.github/workflows/release.yml:26-45,164-166`），Nix 只声明 Linux（`flake.nix:7-10`），文档也列的是 Windows/Linux。
- 影响：macOS 用户没有官方产物，只能自行编译或改用上游。
- 建议：Windows 专属功能已做条件编译并提供非 Windows 回退，macOS 具备编译可行性，但当前 CI 未验证；可增加 `x86_64-apple-darwin`/`aarch64-apple-darwin` 构建与文档，是否发布取决于维护成本。
- 预估：2–3 小时（含 CI 与文档，不含签名/公证）。

### 2.13 云函数事件入口（不计划）

- 上游：`index.py:8-23` 提供腾讯云 SCF 的 `main_handler`/`main_handler_mulit`，配合 `config.serverless=True` 做只读保护；README `README.md:195-240` 给出部署步骤。
- 本项目：CLI 二进制，没有事件函数入口；可通过容器/外部调度运行。
- 结论：不计划实现。Rust 静态二进制不适合直接当 Python 事件函数部署；如确需，可用容器镜像 + 云厂商容器运行时解决。

## 4. 行为差异（不是功能缺失）

| 主题 | 上游 | 本项目 | 说明 |
|---|---|---|---|
| 多账号模型 | 多文件、每文件一个账号 | 单文件多账号，可再用 `run-directory` 批量 | 迁移时按账号拆分/合并即可 |
| 配置升级 | 读到旧版自动升级并回写 | 提供 `migrate-config`，旧版默认只读 | 本项目避免误写回，需用户显式迁移 |
| 青龙通知 | 默认走青龙 `notify.py`，可用 `push_project=1` 切回项目推送 | 明确不执行外部 Python，只读 YAML `notifications` | 安全取舍，已在文档说明 |
| 云游戏 token 失效 | 清空 token 并关闭对应开关 | 只报告认证失败，不自动删除 | 本项目避免误删，需用户确认 |
| 推送渠道失败 | 单渠道异常继续其它渠道 | 同 | 已对齐 |
| 推送结果判定（PushMe） | 校验响应体为 `success`（`push.py:112-137`） | 仅校验 HTTP 200（`src/push/mod.rs:507-510`） | 失败可能被记为发送成功，建议补响应体判断 |
| 批量运行确认 | 可交互等待回车 | 直接执行，可用 `--prefix`/`--task` 控制 | 自动化友好，少了确认 |
| 页面活动 | 硬编码活动有效期 | 同样只保留已过期活动并跳过 | 双方都没有新活动实现 |
| K8s 形态 | Deployment + 容器内 cron | CronJob + 外部调度 | 本项目更符合 K8s 习惯 |
| 容器分发 | Docker Hub + GHCR | 仅 GHCR | 见 2.4 |
| 日志 | 可完全自定义 `logging.ini` | 级别/目录/前缀 | 见 2.8 |

## 5. 上游已移除或明确不支持，无需跟进

| 项 | 上游现状 | 结论 |

## 6. 本项目相对上游的额外能力

- 验证码平台客户端（端点、超时、错误分类、失败重试、脱敏）。
- 账号级代理与 Telegram 独立代理；SOCKS5/SOCKS5H。
- 游戏签到提交后复查、仅未完成才重试；社区任务按米游币任务 ID 与差值复查；状态未知时停止而不是盲目重试。
- 多账号单文件、`run-directory` 批量、`schedule` 常驻、`automation`/`create-launcher` 系统集成。
- `doctor` 离线/在线诊断、`validate-config`、`notification list/test`、`config init/setup/edit`、备份/恢复、`migrate-config`、`update check`。
- 文本/JSON 双报告、稳定退出码、8 种任务状态。
- 敏感值脱敏、配置文件 0600、只读模式、`${ENV}` 注入、错误信息不泄露 URL 凭据。
- CI：fmt、clippy、测试、TLS 依赖检查、多架构发布、Nix 构建、TLS 冒烟测试。

## 7. 建议

1. 先做 P1：`qbot` 渠道 + `push.ini` 迁移。前者补齐唯一的通知渠道缺口，后者决定存量用户能否平滑切换。
2. 再做 P2：SMTP HTML（建议背景图默认关闭）、Docker 定时/compose、Nix Home Manager。三项都不影响核心任务，但直接影响部署体验。
3. P3 按需：`qbot` openid 工具、日志自定义、UA 自动补版本、Bark 预设、多用户确认、macOS 构建。
4. 不建议投入：`server.py` 式交互控制台（价值低、维护成本高）、云函数入口（运行模型不匹配）。
5. 验收建议：为每个新增项补对应单测/文档；Docker 与 Nix 改动需要实际拉取镜像和 `nix flake check`；`qbot` 需要真实机器人凭据做一次发送验证。
