# 与上游 MihoyoBBSTools 的功能差异

> 对比时间：2026-11-26（v2.2.0 复核；初版 2026-11-21）
>
> 上游：`D:\GitHub\Womsxd\MihoyoBBSTools`，HEAD `c401f21`（2026-11-25，米游社客户端 `2.117.0`）
>
> 本项目：`D:\GitHub\bcmdy\mihoyo-bbs-tools-rs`，HEAD `185cf9f` / 标签 `v2.2.0`（2026-11-26）
>
> 口径：只比较用户可感知的功能与运行方式；不比较实现语言、代码质量和上游疑似缺陷。结论来自双方源码、配置示例和文档的静态对照，未对上游做运行验证。本文合并了原先独立的《上游更新评估》，以后上游变更直接追加到本文第 6 节。

## 1. 结论

核心自动化能力已经对齐：国服 6 款游戏、HoYoLAB 5 款游戏、3 项云游戏、米游社 9 个板块的社区任务、米游币任务判定、多账号、凭据刷新与 V2 换票、青龙、DaCapo、旧配置迁移、常驻调度都有对应实现；验证码、代理、复查重试、报告、诊断和安全处理还强于上游。

按“是否影响任务成败”区分：**核心功能（4 个任务族 + 4 项支撑能力）已全部对齐并有增强**。v2.2.0 又补充了通行证 V2 换票、签到确认窗口、配置原子替换、通知业务码校验、日志保留与调度可取消等待，并新增 JSON 报告 `schema_version: 2`（只增可选字段），核心链路的领先幅度进一步扩大。剩余缺口集中在非核心的通知、部署与迁移兼容三块：

1. **通知**：SMTP 只有纯文本，没有上游的 HTML 模板与随机背景图；PushMe 未校验业务成功码。
2. **部署与分发**：Docker 镜像没有上游的容器内定时（`CRON_SIGNIN`/`MULTI`）和 `docker-compose.yml`；Nix 只有 package，没有上游的 Home Manager 模块；没有 macOS 构建。
3. **迁移兼容**：旧 `push.ini` 不自动转换；`logging.ini` 自定义日志、自定义 UA 自动补版本号、Bark 预设图标等细节未对齐。

### 1.1 核心功能与非核心功能的划分

| 分类 | 内容 | 说明 |
|---|---|---|
| **核心任务** | 国内游戏签到、HoYoLAB 签到、米游社社区任务、云游戏签到 | 决定“是否签到成功”的唯一产出 |
| **核心支撑** | DS 签名、凭据与 Cookie 体系、提交后复查与重试、验证码求解 | 缺任一都会让核心任务失败 |
| **非核心（外围）** | 通知渠道、部署形态（Docker/K8s/Nix/自动化）、配置适配（青龙/DaCapo/批量）、诊断与交互向导、日志呈现、迁移兼容 | 影响易用性与运维，不影响签到正确性 |

## 2. 缺口逐项说明

### 2.1 `push.ini` 配置迁移（P1）

- 上游：通知完全由 `config/push.ini` 承载，支持 `AutoMihoyoBBS_push_path` / `AutoMihoyoBBS_push_name` 指定路径（`push.py:34-58`），`push_server` 还支持逗号分隔多服务（`push.py:526-559`）。
- 本项目：通知写在 YAML 的 `notifications` 节点；旧 v11–v15 配置迁移时会显式丢弃 `push` 字段并告警（`src/config/legacy.rs:241`）。
- 影响：从 Python 版迁移的用户必须手工把推送段改写成 `notifications.providers[]`，否则不会收到任何通知。
- 建议：新增 `migrate-push`（或并入 `migrate-config`）读取 `push.ini`，把 `push_server`、`push_token`、`block_keys`、`error_push_only`、各渠道段映射为 `NotificationProvider`；多服务逗号写法拆成多个 provider，无法映射的字段输出明确清单。
- 预估：2–3 小时。

### 2.2 SMTP HTML 邮件与随机背景图（P2）

- 上游：`push.py:202-249` 读取 `assets/email_example.html`，把标题、正文、背景图渲染成 HTML 邮件；背景图来自 `https://www.loliapi.com/acg/pc/`，`[smtp] background` 可关闭。
- 本项目：`src/push/smtp.rs` 用 lettre 发送纯文本（`标题 + 两行换行 + 报告`），没有 `background`、`html` 之类字段。
- 影响：只影响邮件观感，不影响送达。
- 建议：内置精简 HTML 模板，背景图做成可选开关且默认关闭，避免依赖第三方随机图 API；保留纯文本回退。
- 预估：1–2 小时。

### 2.3 容器内定时、compose 与 Docker Hub（P2）

- 上游：`docker.py:17-50` 在容器内按 `CRON_SIGNIN`（默认 `30 9 * * *`）循环执行，`MULTI=TRUE` 时走多配置；根目录有 `docker-compose.yml`；镜像同时发布 Docker Hub 与 GHCR。
- 本项目：`Dockerfile` 是 `ENTRYPOINT ["MihoyoBBSToolsRS"]` + `CMD ["run"]`，即一次性执行；没有 `docker-compose.yml`，全仓库没有 `CRON_SIGNIN`/`MULTI`；容器 workflow 只发布 GHCR。
- 影响：从上游 compose 迁移的容器用户会发现“起容器后不会自动每天跑”；拉取习惯也要从 Docker Hub 改为 GHCR。此外上游任意入口都读 `AutoMihoyoBBS_config_path`/`AutoMihoyoBBS_config_prefix`，本项目只在 `qinglong` 子命令中读取同名变量，普通 `run` 需要用 `--config`。
- 建议：增加 `docker-compose.yml` 示例默认 `command: ["schedule"]`；兼容 `CRON_SIGNIN`/`MULTI` 或在启动时提示改用 `schedule`；按需增加 Docker Hub 发布。
- 预估：2–4 小时（含文档）；Docker Hub 另加 0.5 小时。

### 2.4 Nix Home Manager 模块（P2）

- 上游：`flake.nix` 提供 `homeModules.default`，含 `services.mihoyo-bbs-tools.{enable,onCalendar,persistent,settings,extraEnvironments}`，生成 systemd user service 与 timer（`RandomizedDelaySec = "20min"`）。
- 本项目：`flake.nix` 只有 `packages` 和 `apps`，没有 `homeModules`/`nixosModules`。
- 影响：Nix 用户需要自己写 systemd 单元或 cron。
- 建议：增加 `homeModules.default`，把 `settings` 渲染到用户配置目录并生成 user service + timer；与 `runtime.schedule` 二选一，避免双跑。
- 预估：2–4 小时。

### 2.5 `server.py` 式常驻控制台（P3，可不做）

- 上游：`server.py` 提供常驻交互模式，支持 `stop/exit`、`reload`、`test`、`single`、`multi`、`mod 1|2`、`time N`、`show`、`add 'cookie'`、`set user attr value`、`help`。
- 本项目：`schedule` 每轮重新加载配置，`automation`/`create-launcher` 负责系统级定时，`config` 子命令负责离线改配置；没有运行中的交互控制台。v2.2.0 增加了 `schedule.poll_seconds`、Ctrl+C/SIGTERM 退出信号与配置重载恢复，运行期可安全停止，但仍不能像上游那样在线 `reload`/改间隔/加账号。
- 影响：对习惯 screen + 控制台的用户是体验差异；对定时无人值守场景没有影响。
- 建议：不建议现在实现交互式 REPL；在文档中说明 `schedule` + `config` + `notification test` 的替代路径。
- 预估：6–10 小时（价值低）。

### 2.6 `logging.ini` 自定义日志（P3）

- 上游：存在 `config/logging.ini` 时用 `logging.config.fileConfig` 完全接管日志。
- 本项目：`runtime.logging` 支持 `enabled`、`directory`、`file_prefix`、`retention_days`（v2.2.0 新增，默认省略表示保留全部），格式固定、按日滚动；级别可配，`RUST_LOG` 可覆盖。仍不支持上游的 formatter/handler 自定义。
- 影响：需要自定义日志格式或多 handler 的用户无法直接迁移。
- 建议：优先级低；如需支持，提供少量格式化选项比引入通用日志配置更符合本项目风格。
- 预估：1–2 小时。

### 2.7 Bark 预设图标名（P3）

- 上游：`push.py:350-361` 把 `icon=genshin` 等预设名拼成 jsdelivr 图标 URL。
- 本项目：`icon` 原样作为查询参数传给 Bark。
- 建议：接受 URL 的同时兼容几个预设名，映射到与上游相同的图标地址。
- 预估：0.5 小时。

### 2.8 多用户交互确认与 `AutoMihoyoBBS_autorun`（P3）

- 上游：`main_multi.py` 非 autorun 时列出配置文件并等待回车，支持 `AutoMihoyoBBS_autorun=1` 跳过。
- 本项目：`run-directory` 发现配置后直接执行，没有确认步骤。
- 建议：可加 `--yes`/`--no-confirm` 显式开关，默认保持非交互。
- 预估：0.5 小时。

### 2.9 macOS 官方构建（P3）

- 上游：Python 版可在 macOS 运行，Home Manager 说明也明确 Linux 与 macOS 都支持。
- 本项目：发布矩阵只有 Linux x86_64/arm64/armv7 与 Windows x86_64，Nix 只声明 Linux。
- 建议：Windows 专属功能已做条件编译并提供非 Windows 回退，具备编译可行性但 CI 未验证；可增加 `x86_64-apple-darwin`/`aarch64-apple-darwin` 构建与文档。
- 预估：2–3 小时（含 CI 与文档，不含签名/公证）。

### 2.10 PushMe 响应体校验（P3）

- 上游：`push.py:112-137` 要求 HTTP 200 且响应体为 `success`。
- 本项目：v2.2.0 已加入统一业务码校验框架（`CompatSuccessRule`，覆盖企业微信、钉钉、飞书、WxPusher、CQHTTP、Server酱³），但 PushMe 仍归入 `StatusOnly`，只看 HTTP 状态，可能把失败记为发送成功。补齐只需新增一条规则。
- 建议：为 PushMe 增加“响应体等于 `success`”的成功规则。
- 预估：0.5 小时。

### 2.11 云函数事件入口（不计划）

- 上游：`index.py` 提供腾讯云 SCF 的 `main_handler`/`main_handler_mulit`，配合 `config.serverless=True` 做只读保护。
- 本项目：CLI 二进制，没有事件函数入口；可通过容器/外部调度运行。
- 结论：不计划实现；如确需，可用容器镜像 + 云厂商容器运行时解决。

## 4. 行为差异（不是功能缺失）

| 主题 | 上游 | 本项目 | 说明 |
|---|---|---|---|
| 多账号模型 | 多文件、每文件一个账号 | 单文件多账号，可再用 `run-directory` 批量 | 迁移时按账号拆分/合并即可 |
| 配置升级 | 读到旧版自动升级并回写 | 提供 `migrate-config`，旧版默认只读 | 本项目避免误写回 |
| 青龙通知 | 默认走青龙 `notify.py`，可用 `push_project=1` 切回 | 明确不执行外部 Python，只读 YAML `notifications` | 安全取舍 |
| 云游戏 token 失效 | 清空 token 并关闭对应开关 | 只报告认证失败，不自动删除 | 本项目避免误删 |
| 推送渠道失败 | 单渠道异常继续其它渠道 | 同 | 已对齐 |
| 批量运行确认 | 可交互等待回车 | 直接执行，可用 `--prefix`/`--task` 控制 | 自动化友好 |
| 网页活动 | 硬编码活动有效期 | 同样只保留已过期活动并跳过 | 双方都没有新活动实现 |
| K8s 形态 | Deployment + 容器内 cron | CronJob + 外部调度 | 本项目更符合 K8s 习惯 |
| 容器分发 | Docker Hub + GHCR | 仅 GHCR | 见 2.3 |
| 日志 | 可完全自定义 `logging.ini` | 级别/目录/前缀/保留天数 | 见 2.6 |

## 5. 上游已移除或明确不支持，无需跟进

| 项 | 上游现状 | 结论 |
|---|---|---|
| 赛事/七圣召唤（`competition`） | 2025-05 已移除自动化，仅剩空 `run_task()` 与废弃配置 | 不跟进；本项目迁移时已丢弃并告警 |
| GitHub Actions 每日签到 | 明确拒绝，检测到 `GITHUB_ACTIONS=true` 直接退出 | 不跟进；本项目另有仅官方仓库可用的可选定时工作流 |
| 云函数入口 | 支持，但依赖 Python SCF 运行时 | 不计划，见 2.11 |
| CNB 镜像同步、`docker_full/` | 仓库基础设施/历史镜像 | 不属于用户功能 |
| 依赖缺失 `-99` 状态 | 青龙 Python 依赖缺失时提示 | 静态二进制无此问题 |
| 青龙 `notify.py` 集成 | 默认使用 | 本项目主动不执行外部 Python |

### 6.4 qbot 推送与 OpenID 工具的实施记录

2026-11-27 补齐了原 2.1（`qbot` 渠道）与原 2.6（openid 工具）两项。

| 能力 | 实现位置 |
|---|---|
| `qbot` 配置结构（appid/secret/openid/api_url） | `src/config/mod.rs` 的 `NotificationProvider::Qbot` |
| 渠道校验（纯数字 appid、必填 secret/openid） | `src/config/mod.rs` 的 `validate_provider` |
| 两段式发送（取 token → 发单聊） | `src/push/mod.rs` 的 `QbotProvider` |
| 业务码判定（失败也返回 HTTP 200） | `QbotTokenResponse`/`QbotMessageResponse` 的 `code` 校验 |
| 配置向导与字段菜单 | `src/config/interactive.rs` 的 `provider_types`/`provider_fields` |
| OpenID 获取命令 | `src/cli.rs` 的 `qbot-open-id`、`src/main.rs` 的 `execute_qbot_openid` |
| 网关与 WebSocket | `src/push/qbot.rs`（HTTP upgrade + 自实现帧编解码） |
| 写回配置 | `src/config/editor.rs` 的 `set_qbot_open_id` |

与上游的差异（有意保留）：

- **不新增依赖**：`sec-websocket-accept` 校验需要 SHA-1，这里内置最小实现而不是引入 `sha1` crate；`Cargo.lock` 保持不变（CI 使用 `--locked`）。WebSocket 帧编解码亦自行实现，没有引入 WebSocket 生态。
- **复用既有 HTTP 客户端**：网关地址与令牌请求走项目既有的代理与 TLS 配置，与其它请求行为一致；为此新增 `HttpClient::get_upgrade_once`。
- **令牌不缓存**：每次运行只推送一次，缓存收益抵不过失效判断复杂度；令牌不落盘、不入日志。
- **失败按业务码判定**：上游脚本仅检查 HTTP 200 与 `id` 是否存在，这里对两步都校验 `code`。

## 7. 本项目相对上游的额外能力

- 验证码平台客户端（端点、超时、错误分类、失败重试、脱敏）。
- 通行证 V2 换票：V2 优先刷新并回退旧接口，社区任务前补齐缺失的 `cookie_token`/`ltoken`，V1/V2 别名自动同步。
- 国内签到 User-Agent 版本自动归一化（等价上游 `get_useragent`）：自定义 UA 无需随米游社升级手工改版本。
- QQ 机器人单聊渠道与 `qbot-open-id` 工具：自动获取 OpenID 并写回配置，无需手工抓包。
- 社区签到 1008「打卡失败或重复打卡」按复查结论定论，不再误报执行失败。
- 账号级代理与 Telegram 独立代理；SOCKS5/SOCKS5H。
- 游戏签到提交后复查、仅未完成才重试；社区任务按米游币任务 ID 与差值复查；状态未知时停止而不是盲目重试。
- 多账号单文件、`run-directory` 批量、`schedule` 常驻、`automation`/`create-launcher` 系统集成。
- `doctor` 离线/在线诊断、`validate-config`、`notification list/test`、`config init/setup/edit`、备份/恢复、`migrate-config`、`update check`。
- 文本/JSON 双报告、稳定退出码、8 种任务状态；JSON 只增字段的兼容约定与稳定的 `task_id`。
- 签到“提交次数”与“确认查询次数”分离，确认查询不消耗提交次数。
- 配置原子替换、并发冲突保留与受控备份，`.gitignore` 默认忽略含凭据的备份与临时文件。
- 通知渠道业务成功码校验（企业微信、钉钉、飞书、WxPusher、CQHTTP、Server酱³）。
- 日志保留天数清理、调度可取消等待与退出信号。
- 敏感值脱敏、配置文件 0600、只读模式、`${ENV}` 注入、错误信息不泄露 URL 凭据。
- CI：fmt、clippy、测试、TLS 依赖检查、多架构发布、Nix 构建、TLS 冒烟测试、文档链接校验、`cargo-deny`、构建缓存、Windows 测试作业与 CLI 冒烟测试。
