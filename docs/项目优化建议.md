## 1. 范围与判断口径

审查覆盖 `src/`、`tests/`、`Cargo.toml` 与锁文件、GitHub Actions、Docker/Nix，以及现有配置和使用说明。

- **P1**：可能影响凭据保密、配置完整性、任务或通知结果正确性、已声明的构建兼容性，以及正式发布的质量保障。
- **P2**：影响异常恢复、长期运行、可维护性或测试有效性，适合随后集中处理。
- **P3**：潜在效率或行为优化，需要性能基线、上游行为证据或明确需求后决定实施。
- **静态确认**：源码能够直接支持该行为或缺口；不代表已经在真实账号环境复现。
- **待测**：已有可核验的优化入口，但实际收益或风险仍需受控实验确认。

现有安全和业务规则应作为优化约束：副作用请求单次发送，由业务层复查决定是否再次执行；社区首轮按账号配置执行；未知任务只记录；凭据刷新保持次数上限；环境变量、标准输入和只读配置保持现有写回边界。详见 [报告与重试机制修改需求](报告与重试机制修改需求.md) 和 [使用说明](使用说明.md)。

上游渠道和部署能力的兼容需求继续参考 [上游功能差异对比](上游功能差异对比.md)，按用户需求另行排期。

## 3. 凭据、配置与结果正确性

### A01：忽略含凭据的备份与临时文件（P1）

**当前依据：** [.gitignore](../.gitignore#L5) 只忽略 `config/*.yaml`（另忽略 `/target/`、`.env*`、`*.log`）；该模式不递归，`config/backups/` 因而逃逸。[配置备份](../src/config/editor.rs#L1052) 把原配置全文写入**配置文件父目录下的 `backups/`**（[backup_directory](../src/config/editor.rs#L1171)），命名 `{stem}-{YYYYmmdd-HHMMSS}.yaml`（[备份文件名](../src/config/editor.rs#L1079)）。编辑流程还生成 `.session`、`.backup` 和 `.editing` 三种临时文件，见 [会话副本](../src/config/editor.rs#L42)、[替换备份](../src/config/editor.rs#L1041)、[临时路径](../src/config/editor.rs#L1325)；首配暂存另见 [interactive.rs](../src/config/interactive.rs#L165)。

**影响：** 在仓库目录使用配置编辑或备份后，执行 `git add .` 可能把 Cookie、SToken 和通知凭据加入提交；异常退出遗留的临时文件也有同样风险。复核已用 `git check-ignore --no-index` 实测：上述备份与三种临时路径**当前全部未被忽略**，风险是现实存在的。

**建议：** 对默认配置目录增加备份和实际临时文件命名规则的忽略项，继续保留示例配置与测试 fixture。对自定义配置路径，在使用说明中明确其目录需要独立保护；Git 忽略规则只能保护尚未跟踪的文件。

**验收：** 使用 `git check-ignore --no-index` 检查默认真实配置、备份及三种临时路径均被忽略；`config/config.example.yaml` 和迁移 fixture 仍可跟踪。用虚构凭据构造测试路径即可。注意 `release` 使用 `panic = "abort"`，`Drop` 清理不会执行，除忽略规则外还需在启动时清理陈旧的 `*.{pid}.*` 文件兜底。

### A02：配置替换补齐崩溃恢复与并发冲突保护（P1）

**当前依据：** [replace_validated_inner](../src/config/editor.rs#L1026) 的写入序列是：写临时文件 → 校验 → 受控时间戳备份 → 把真实配置重命名为瞬时备份 `yaml.<pid>.backup` → 把临时文件重命名到真实路径。两段重命名之间存在真实路径暂时消失的窗口；[secure_write_new](../src/config/editor.rs#L1329) 只 `write_all`，未 `sync_all`（同模块的 [install_new_config](../src/config/editor.rs#L1195) 与 [write_migrated_config](../src/config/mod.rs#L848) 反而已同步）。编辑会话保存了初始原文，但 [commit](../src/config/editor.rs#L105) 未与真实配置现值比较。另需注意 [persist_refreshed_cookie](../src/config/editor.rs#L791) 经 `mutate_raw_without_backup` 走同一两段重命名且不建备份。

**影响：** 两次重命名之间进程退出，可能留下缺失的配置路径；交互编辑期间另一个进程刷新 Cookie，之后提交旧会话可能静默覆盖新凭据。刷新写回路径不建备份，该覆盖不可从备份恢复。

**建议：** 抽出统一配置持久化组件，使用平台适用的原子替换方式，保留现有校验、受控备份与权限设置，并落实文件同步及必要的目录同步。写入加入互斥或版本比较；比较和替换应处于同一受保护范围，冲突时保留待保存副本并明确报告。

**验收：** 在写入、校验、替换各阶段注入失败，真实路径可以读到完整的新配置或旧配置，重启后能恢复；编辑与刷新交错时不发生静默覆盖；Linux 和 Windows 都验证真实文件系统行为。

### A03：错误与 Debug 边界统一脱敏（P1）

**当前依据：** [expand_string](../src/config/mod.rs#L1443) 在占位符未闭合时把从 `${` 到输入末尾的整段原文放入错误（[L1452](../src/config/mod.rs#L1452)），经 `ConfigError` → `tracing::error!` 输出到控制台与文件日志，泄漏是确定性的；名称非法时只回显 `${name}`。[HttpClientBuilder](../src/http/client.rs#L46) 派生 Debug 且代理字段是原始 `Url`（当前全仓无打印点，属潜在泄漏）；[HTTP 错误转换](../src/http/client.rs#L150) 及其余 8 处保存 reqwest 错误文本，reqwest `Display` 恒追加请求 URL，故为恒带而非「可能」携带。项目已有 SecretString 与通知错误脱敏，需要补齐这些边缘路径。

**影响：** 异常配置片段若混入凭据，会随错误输出；打印 Builder 或底层连接错误时，带认证信息的代理和 URL 参数会被回显。前者已确定发生，后者取决于是否新增打印点。

**建议：** 占位符错误仅报告字段路径和错误类别；Builder 使用脱敏 Debug；HTTP 错误在进入应用错误类型前去除 URL 或转换成安全分类，并把散落在 [push](../src/push/mod.rs#L831) 与 [doctor](../src/doctor.rs#L501) 的脱敏函数收敛到 `http/error.rs` 共用。只在构造侧脱敏，不要改 `HttpError` 枚举语义——认证层依赖 `is_timeout`/`is_connect` 分类。

**验收：** 使用虚构代理密码、URL Token、非法占位符，检查 Display、Debug、控制台、文件日志与 JSON 均不含这些值，同时保留足够的错误类别和字段定位信息。

### A04：提交后复查保留认证失败类型（P1）

**当前依据：** [国内签到复查](../src/service/runner.rs#L562) 和 [HoYoLAB 复查](../src/service/runner.rs#L727) 把实际提交后的所有复查错误统一记录为 `NetworkFailed`，也包括 Cookie 失效。[刷新触发判断](../src/service/credential_refresh.rs#L11) 只检测 `AuthenticationFailed`。缺口限于复查分支：尝试次数用尽分支已正确保留错误类别（[runner.rs](../src/service/runner.rs#L603)、[L776](../src/service/runner.rs#L776)）。`CookieInvalid` 由 [response.rs](../src/checkin/response.rs#L124) 依据 retcode -100/-101/-10001/-10002 产生。

**影响：** 单游戏、单角色提交后认证失效时，用户收到网络问题提示，国内 SToken 刷新也可能无法触发。

**建议：** 抽出 `classify_checkin_error()`（CookieInvalid → AuthenticationFailed、Http → NetworkFailed、其余 → Failed），复查失败的 `Err` 分支改用它；复查失败继续停止提交，但保留原错误类别和“提交结果未知”的上下文。国内认证失败刷新后先只读确认状态，明确未完成后才允许再次提交，并保证刷新最多一次；HoYoLAB 继续使用独立凭据逻辑。

**验收：** Mock `Pending → 提交 → 复查 CookieInvalid`，结果分类为认证失败；国内最多刷新一次，之后先查询状态；查询失败不产生新的签到提交。传输错误仍正确分类为网络失败。

### A05：统一网络重试次数语义（P2）

**当前依据：** [使用说明](使用说明.md#132-runtime-全局运行) 将 `runtime.retry_count` 定义为“额外重试次数”；消费点实际有 5 处、语义分三类：[游戏客户端](../src/service/runner.rs#L156)、[HoYoLAB](../src/service/runner.rs#L170)、[BBS](../src/service/bbs_runner.rs#L1150)、[云游戏](../src/service/cloud_runner.rs#L203) 直接赋给总尝试次数，[通知客户端](../src/push/mod.rs#L363) 则加一，[HTTP 循环](../src/http/client.rs#L129) 使用 `attempts.max(1)`。另有 [update.rs](../src/update.rs#L18) 与 [昵称查询](../src/config/editor.rs#L331) 不读配置、硬编码默认值，[doctor](../src/doctor.rs#L465) 硬编码 1 次。

| retry_count | 游戏 / BBS / 云游戏（`attempts = retry_count`） | 推送鉴权（`retry_count + 1`） | 文档定义的总尝试上限 |
|---:|---:|---:|---:|
| 0 | 1 | 1 | 1 |
| 1 | 1 | 2 | 2 |
| 3 | 3 | 4 | 4 |

**影响：** 相同配置在不同模块中含义不同：游戏类少于文档预期，推送鉴权反而多一次；遇到临时网络故障时用户拿不到文档承诺的重试次数。

**建议：** 在 HTTP 层集中转换“额外重试次数 + 首次请求”（如 `RetryPolicy::for_extra_retries(extra)`，内部取 `extra + 1`），5 处消费点统一改用它，推送鉴权去掉手写的 `+1`，两处硬编码默认值也改走同一构造函数。修改时在发布说明中记录行为差异，继续区分网络重试与 `task_max_attempts`。

**验收：** 对允许网络重试的只读请求，在持续可重试错误下验证配置 0/1/3 分别最多发送 1/2/4 次；成功立即结束，非重试状态立即结束；副作用 POST 与副作用 GET 保持单次发送。同时记录 `retry_count ≥ 1` 时出站请求次数增加 1 对限流风险的影响。

### A06：通知渠道验证业务成功码（P1）

**当前依据：** [兼容通知发送](../src/push/mod.rs#L571) 的 JSON/Form 路径只检查 HTTP 状态。经该路径的渠道包括企业微信机器人、钉钉机器人、飞书机器人、Gotify、Discord、Wxpusher、ServerChan3、CQHTTP 与 IFTTT，即使 HTTP 200 中携带非零 `errcode/code`，仍可能记录为发送成功。[Telegram](../src/push/mod.rs#L655) 已有独立业务响应检查，可作为参照。已有部分校验不能替代：Pushplus 已判 `code == 200`，企业微信应用的 gettoken 已校验 `errcode`；Bark 与 Pushdeer 的 GET 路径同样只查状态码。

**影响：** 用户配置失效、服务拒绝或限流时，报告可能显示通知成功，影响问题定位与自动运行可靠性。

**建议：** 按具体服务协议建立最小响应模型（`errcode`/`code` 均 `Option` + `serde(default)`），检查成功码并输出脱敏错误类别；通用 Webhook 保持空响应与 204 兼容。不要因为增加响应校验而自动重复发送通知。

**验收：** Mock HTTP 200 + 业务错误为 Failed，成功码为 Sent；通用 Webhook 204 空响应仍成功；第三方响应中含虚构 Secret 时不得进入报告。

## 4. 构建、测试与发布

### A07：修正最低 Rust 版本并验证 MSRV（P1）

**当前依据：** [Cargo.toml](../Cargo.toml#L8) 声明 `rust-version = "1.85"`，但 [配置替换](../src/config/editor.rs#L1037) 和 [报告渲染](../src/service/report.rs#L165)、[L180](../src/service/report.rs#L180) 使用 Rust 1.88 才稳定的 let 链。`edition = "2024"` 本身要求 1.85，故 1.85 声明是“过线但不够”，编译必失败于这三处。`stable` 是 [现有 CI](../.github/workflows/ci.yml#L84) 唯一验证的工具链。但 let 链只是语法下界，`reqwest 0.13`/`rustls 0.23`/`thiserror 2` 等依赖的 MSRV 可能更高。

**影响：** 用户按最低版本声明构建仍会失败；stable 检查无法防止最低版本兼容性回退。

**建议：** 先把声明上修到 `1.88`，并增加独立 MSRV 任务用 1.88 工具链执行 `cargo check --locked`，同时保留 stable 检查；再由实测结果决定是否继续上修。不要一次写死更高版本，也不要只靠 stable——后者无法阻止 MSRV 回退。把 let 链改写为等价嵌套是另一条路径，但牺牲可读性，建议仅在必须支持 1.85 时才做。

**验收：** 声明的最低工具链可以编译锁定依赖与全部生产源码；引入更高版本特性时，最低版本 CI 能发现回退。若 1.88 仍不足以编译锁定依赖，MSRV 任务须给出明确失败，而不是让用户在本地构建时才发现。

### A08：发布验证同一提交并正确记录 SHA（P1）

**当前依据：** [发布工作流](../.github/workflows/release.yml#L241) 只依赖 Linux/Windows 构建，没有测试和 Clippy 前置条件；完整质量检查位于另一个覆盖分支 push、PR 和手动执行、未覆盖标签 push 的 [CI 工作流](../.github/workflows/ci.yml#L60)。手动发布在 [检出指定标签](../.github/workflows/release.yml#L74) 前已经设置 `GIT_COMMIT = github.sha`，Windows 分支也有相同顺序。

**影响：** 编译成功但测试失败的标签可能发布；从 main 手动发布旧标签时，产物记录的 SHA 可能属于触发分支，影响追溯。

**建议：** 抽出可复用质量检查，在最终发布的 tag/ref 上执行，让正式发布与镜像推送依赖同一提交的成功结果。最终检出后通过 `git rev-parse HEAD` 生成构建 SHA，统一用于程序版本输出和构建摘要。

**验收：** 在可编译但测试失败的临时标签上，正式发布和正式镜像推送被阻止；手动构建另一个标签时，所有架构产物的 `version` 提交值与该标签实际 SHA 相同。验证使用测试仓库或不发布的检查任务。

### A09：Nix 工作流实际构建软件包（P2）

**当前依据：** [nix.yml](../.github/workflows/nix.yml#L57) 仅执行 `nix flake check`；[flake.nix](../flake.nix#L16) 定义 `packages`/`apps`，但没有 `checks` 输出。`nix flake check` 只构建 `checks`，不会构建 `packages`，因此证明不了程序完成编译和安装。

**影响：** Nix 包中的编译、依赖或安装脚本错误可能无法被现有检查发现。

**建议：** 为两个现有 system 显式执行 `nix build .#packages.<system>.default --print-build-logs --no-write-lock-file`，或定义真实 checks；之后检查产物与安装文件。

**验收：** x86_64-linux、aarch64-linux 都生成可执行包；运行 `version` 成功，说明、示例配置和 DaCapo 模板安装路径正确。

### A10：锁文件更新先验证，补依赖健康检查（P2）

**当前依据：** [lockfiles.yml](../.github/workflows/lockfiles.yml#L31) 重新生成 Cargo/Nix 锁文件后，直接 [提交并推送 main](../.github/workflows/lockfiles.yml#L63)，中间没有编译或测试步骤。现有工作流未配置依赖安全审计或许可证策略检查，仓库也没有 `deny.toml`。

**影响：** 依赖更新可能引入 MSRV、构建或行为回退。默认 GITHUB_TOKEN 产生的推送通常不会再次触发普通 push 工作流，后续 CI 不能作为这一步的可靠保障。

**验收：** 不兼容锁文件不能直接更新 main；依赖检查发现问题时给出明确失败或可追踪例外。本次未执行漏洞审计，因此这里没有认定当前依赖存在已知漏洞。

### A11：Windows 执行测试与离线 CLI 回归（P2）

**当前依据：** [CI quality](../.github/workflows/ci.yml#L60) 在 Ubuntu 上运行测试，Windows 主要执行构建（[矩阵](../.github/workflows/ci.yml#L131) 只跑 `cargo build`）；`tests/` 只有 [TLS smoke](../tests/tls_smoke.rs) 且带 `#[ignore]`，实际 208 个测试分布在源码模块中，全部可离线执行。Windows 专有实现仍有盲区：[终端输入](../src/config/input.rs#L160) 的 Kernel32 FFI 无测试；[本地通知](../src/push/windows_toast.rs#L51) 的 `unsupported_platform` 用例是 `#[cfg(not(windows))]`，在 Windows 上会被编译掉；自动运行管理用 `cfg!` 运行时判断并调用 `powershell.exe`/`Register-ScheduledTask`，不可离线验证。

**验收：** Linux/Windows 都执行离线测试；CLI 用虚构配置验证退出码、stdout/stderr 和 schema，确认只读运行不改写文件；测试不依赖真实账号、桌面通知或任务计划安装。验收记录中须写明未覆盖项：Kernel32 FFI、Windows toast 发送、计划任务安装。

## 5. 长期运行与维护性

### A12：只读 HTTP 的退避、读取超时与预算（P2）

**当前依据：** [HTTP 请求循环](../src/http/client.rs#L139) 将成功响应的 JSON 读取错误统一映射为 Decode；[等待逻辑](../src/http/client.rs#L152) 对可重试状态采用线性等待（`base_delay * (attempt + 1)`），没有使用 Retry-After，也没有抖动和整体重试时间预算。只读与副作用靠方法名区分：`get_json(_with)` 可重试，`*_once*` 系列单次发送，没有显式标记。

**影响：** 响应头成功但响应体超时无法使用已有重试策略；多个实例可能同时重试。调整具体退避参数的收益需要测量。

**建议：** 对安全的只读请求区分读取超时、传输中断和 JSON 语法错误；尊重有上限的 Retry-After，加入抖动与总时间预算。解析错误保持可诊断，避免无意义重试。

**验收：** 429 等待遵守服务器建议和本地上限；响应体超时按只读策略重试并保留正确分类；非法 JSON 不盲目重试；副作用请求的单次发送规则不变。

### A13：日志保留策略与初始化失败诊断（P2）

**当前依据：** [DailyFileAppender](../src/file_logging.rs#L9) 按日滚动并追加文件（[滚动逻辑](../src/file_logging.rs#L30)），没有清理策略；[LoggingConfig](../src/config/mod.rs#L165) 只有开关、目录和前缀三个字段。[日志初始化](../src/main.rs#L823) 创建 appender 失败时退回 stderr，没有解释文件日志为何不可用；另一处静默降级是 [initial_runtime](../src/main.rs#L601) 用 `.ok()` 吞掉整个配置加载错误，此时 logging 直接为 `None`，同样无提示。文件名为 `{stem}_YYYY-MM-DD.log`（[命名规则](../src/file_logging.rs#L75)）。

**影响：** 常驻或长期自动运行的日志持续增长；无人值守环境可能很久才发现日志没有落盘。

**建议：** 在 `LoggingConfig` 增加 `retention_days: Option<u64>`（`#[serde(default)]`，默认 `None` 即保留全部，完全向后兼容），并同步加入 [未知字段白名单](../src/config/mod.rs#L1507)，否则老配置会被误报未知字段。清理范围严格限定为受控目录内、文件名严格匹配 `{stem}_YYYY-MM-DD.log` 的普通文件，不递归、不跟随符号链接。初始化或清理失败时给出明确诊断。记录典型运行的增长量，再确定默认保留策略。

**验收：** 保留边界正确，其他前缀和用户文件不受影响；日志目录不可写时能看到原因；日志维护故障不会改变已确认的业务任务结果。

### A14：常驻调度的取消与配置重载恢复（P2）

**当前依据：** [schedule 循环](../src/main.rs#L113) 每轮加载配置，失败会直接退出；[等待函数](../src/service/scheduler.rs#L5) 只有完整间隔 sleep，没有等待期间的配置重读或取消处理。进程本身也没有任何信号处理：全仓无 `tokio::signal`/`ctrl_c`/`SIGINT`，[tokio 特性](../Cargo.toml#L29) 仅 `macros,rt,time`。另需注意 `run_on_start: false` 的首轮等待（[main.rs](../src/main.rs#L127)）同样不复查 `enabled`。

**影响：** 外部编辑产生短暂无效 YAML 时进程退出；关闭 `schedule.enabled` 需等到间隔结束才能生效。

**建议：** 初次配置错误明确失败；运行中重载失败时暂停新任务、限频重读，恢复有效配置后继续。等待改为可取消的轮询：`tokio::select!` 同时监听退出信号与配置检查，`Cargo.toml` 的 tokio 特性需补 `signal` 与 `sync`；新增的 `schedule.poll_seconds` 须加入 [未知字段白名单](../src/config/mod.rs#L1514)。退出前保存已完成报告并刷新日志。取消只在轮次边界与等待期生效，不要中断进行中的提交，避免重复签到。

**验收：** 等待期间关闭开关能在约定短周期内退出；无效配置期间不启动新动作，恢复后继续；取消后不开始下一账号，未知提交状态不导致重复提交。Linux 用 `SIGINT`/`SIGTERM` 验证，Windows 只能在控制台按 Ctrl+C（`Stop-Process` 属强制终止，不触发处理），须在验收记录中写明该限制。

### A15：稳定报告标识与结构化业务数据（P2）

**当前依据：** [TaskRecord](../src/service/report.rs#L19) 只有 account/task/subject/outcome/message，除 outcome 外主要是显示文本；[摘要判断](../src/service/report.rs#L257) 依赖“米游币”等中文**常量等值比较**（`record.task == "米游币"`），[处理建议](../src/service/report.rs#L314) 的 message 子串仅 ASCII `stoken`/`mid`，另有 `task.contains("通知")`。首屏计数按所有记录统计，辅助摘要也参与；[JSON 输出](../src/main.rs#L509) 已有 schema_version 入口（当前写死 1）。

**影响：** 修改中文文案可能改变业务汇总，下游需要解析 message 才能获得奖励、币数和尝试次数；记录数与实际任务数不完全等价。

**建议：** 增加稳定 `task_id`、`record_kind`、错误代码和可选业务字段（如 `details.reward`/`details.coin`/`details.attempts`），新增字段一律 `#[serde(skip_serializing_if = "Option::is_none")]`；明确任务记录、诊断记录与摘要的统计口径，文本仅负责展示。JSON 把 schema_version 升到 2 并在发布说明写迁移规则；若要兼容 1.x 读者，可保留版本号只加可选字段，但语义必须择一并写清。

**验收：** 改中文文案不影响汇总和处理建议；JSON 可直接读取奖励、币数、尝试次数；辅助摘要不被误计为业务任务；保持现有按账号报告内容和脱敏规则。

## 6. 需要测量后实施的优化

### A16：统一 HTTP 工厂并复用账号连接池（P3）

**当前依据：** [国内与 HoYoLAB](../src/service/runner.rs#L152)、[BBS](../src/service/bbs_runner.rs#L1146)、[云游戏](../src/service/cloud_runner.rs#L199) 各自硬编码超时、重试与代理后构建客户端；另有第 4 份内联在 [runner.rs](../src/service/runner.rs#L170)、第 5 份在 [push](../src/push/mod.rs#L356)。[任务入口](../src/main.rs#L779) 串行调用这些模块，同一账号一次运行可能重复建立连接池。

**验收与决策：** 不同代理账号不混用连接；比较客户端构造次数、连接次数及整体耗时，再决定是否扩大复用。默认串行和既定风控等待作为基准条件，性能提升幅度以测量结果为准。

### A17：Cargo 缓存与按变更范围运行 CI（P3）

**建议：** 先记录冷/热构建基线，再按 OS、工具链、Cargo.lock 配置缓存；按变更范围选择检查。纯文字修改保留文档链接、示例与打包路径验证，代码和依赖变更执行完整质量检查。

**验收与决策：** 比较耗时、缓存命中率和产物一致性；验证错误路径不会跳过必要检查。发布包包含使用说明与模板，调整触发规则时仍需保障打包有效。

### A18：游戏签到独立的状态确认窗口（P3）

**当前依据：** [国内游戏签到](../src/service/runner.rs#L479) 和 [HoYoLAB 签到](../src/service/runner.rs#L649) 提交后立即查询，仍为 Pending 时可以进入下一次提交；社区流程已有确认等待。游戏成功响应但持续 Pending 的部分路径目前归为网络失败。

**潜在影响：** 如果上游状态存在短暂同步延迟，可能快速耗尽业务尝试次数。当前审查没有证明线上已经发生该场景。

**建议：** 先用 Mock 验证延迟状态序列，再确认上游一致性行为；必要时分离“提交次数”与“确认查询次数”，在有限窗口中等待并只读确认。同步超时使用准确分类，保持最大提交次数约束。

**验收与决策：** `Pending → 提交成功 → Pending → Pending → 已签到` 仅提交一次；持续 Pending 有明确时间和次数上限；确认查询失败不再次提交。根据确认延迟和额外请求成本决定默认窗口。
