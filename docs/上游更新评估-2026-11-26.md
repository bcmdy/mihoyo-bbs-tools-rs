### 2.3 `c767381`：V2 Cookie 获取（唯一功能性变化）

#### 上游做了什么

新增 `login.exchange_token_by_stoken(target)`（`login.py:87-151`），通过通行证 V2 换票接口为 Cookie 补齐 V2 字段：

- 请求：`POST https://passport-api.mihoyo.com/account/ma-cn-session/app/exchange`
- 请求体（紧凑 JSON，**原始字节参与签名**）：`{"dst_token_type":<2|4>,"src_token":{"token":"<stoken>","token_type":1},"mid":"<mid>"}`
- 签名：`DS = t,r,md5("salt=<passport_salt>&t=<t>&r=<r>&b=<body>&q=")`，其中 `passport_salt = "JwYDpKvLj6MrMqqYU6jTKF17KNO2PXoS"`（`setting.py:9`）
- 请求头新增：`x-rpc-app_id`（即原 `verify_key` 值的复用，`setting.py:11-12`）、`x-rpc-sdk_version` 与 `x-rpc-account_version`（`2.44.0`，`setting.py:15`）、`x-rpc-lifecycle_id`（进程内 UUID，`tools.py:43-58`、`main.py:116`）
- 目标类型：`2` = LToken，`4` = CookieToken（`login.py:153-160`）
- 错误处理：`retcode` 为 `-100`/`-3260` 视为 SToken 失效并清理；其它非 0 视为 Cookie 错误

随后在 `build_account_cookie()`（`login.py:222-273`）中：

- 缺 `ltoken_v2`/`ltoken` → 换 LToken 补 `ltoken_v2`/`ltuid_v2`/`ltmid_v2`
- 缺 `cookie_token_v2`/`cookie_token` → 换 CookieToken 补 `cookie_token_v2`/`account_id_v2`/`account_mid_v2`
- 补齐后调用 `sync_cookie_aliases()`（`login.py:291-306`）：V2 字段存在时把 `ltoken`/`ltuid`/`account_id`/`cookie_token` 同步为同值
- `update_cookie_token()`（`login.py:163-193`）优先走 V2 换票，无 mid 时才回退旧接口

入口在 `main.handle_login()`（`main.py:59-63`）：有 `stoken` 且有 `mid` 时执行一次补齐。

#### 本项目现状

- 刷新路径：`src/auth/client.rs:123-152` 只用旧接口 `getCookieAccountInfoBySToken` 换取 `cookie_token`，成功后 `Credentials::replace_cookie_token` 只替换 `cookie_token` 一个键（`src/auth/credentials.rs:188-193`、`src/auth/cookie.rs:108-112`）。
- 触发时机：仅在业务明确返回认证失效后刷新一次（`src/service/credential_refresh.rs:18-48`，调用点 `src/service/runner.rs:86`、`src/service/bbs_runner.rs:75`）。
- 无 `ltoken_v2`、`cookie_token_v2`、passport 换票、`x-rpc-lifecycle_id`、`x-rpc-sdk_version` 等实现（全仓库检索无命中）。
- BBS 请求分两套 Cookie：`stoken_cookie()` 拼的 App Cookie（`src/service/bbs_runner.rs:144`）和原始 Cookie 作为 Web Cookie（:158）。

#### 这个变化要不要跟进

需要区分两件事：

**(a) 上游为什么要做**：从代码看是“被动补齐”——用户从浏览器拿到的 Cookie 可能只有 V1 字段或缺少 `cookie_token`，上游现在会主动换票补全，并在 V2 存在时让 V1 别名同值。它的实际效果是：**减少因 Cookie 字段陈旧导致的社区任务失败**，而不是修复某个已知接口变更。

**(b) 本项目受影响程度**：本项目对 Cookie 的要求更严格——`hydrate_from_cookie` 要求同时具备 Cookie、SToken、数字 UID，V2 SToken 还必须带 MID（`src/auth/credentials.rs:149-168`）；`docs/使用说明.md:116-126` 也要求用户提供完整 Cookie。因此“缺字段导致失败”的场景比上游少。但仍有两个真实缺口：

1. 刷新只写 `cookie_token`，若用户 Cookie 里只有 `cookie_token_v2` 而没有 `cookie_token`，`RefreshOnce::refresh_cookie_token` 会直接返回 `MissingCookieToken`（`src/auth/client.rs:174-178`），无法刷新。
2. 换票接口能同时拿到 LToken，而 LToken 是 HoYoLAB 和部分 Web 接口的凭据；本项目 HoYoLAB 使用独立 Cookie，不会因为缺 LToken 而失败，所以这一半价值较低。

**建议方案（分两步）**：

- **第一步（建议做）**：把刷新结果写入正确的键。若原 Cookie 使用 `cookie_token_v2`（或 SToken 为 `v2_` 前缀），刷新结果应写入 `cookie_token_v2` 并同步 `cookie_token` 别名；同时保留现有旧接口作为回退。涉及 `src/auth/cookie.rs`、`src/auth/credentials.rs`、`src/auth/client.rs`、`src/mihoyo.rs`（新增 passport salt 与版本号常量）、`src/service/credential_refresh.rs`。约 2–3 小时，含单测。
- **第二步（可选）**：实现 V2 换票接口本身，用于“用户缺 `cookie_token` 但 SToken 有效”的自动补齐。需要 `post_json_once_body_raw` 之类的原始字节 POST（当前 `post_json_once` 用 serde 重新序列化，**字节可能与签名不一致**，这是关键实现风险）、passport DS 签名、`x-rpc-lifecycle_id`（`uuid` 目前只启用了 `v3`，需要加 `v4` 特性或用 `rand` 生成）。约 2–4 小时，含 wiremock 测试；真实联调需要有效 SToken 与 MID。

若只做第一步，建议同步在 `docs/使用说明.md` 的 13.4.1 节说明“刷新会写回 V2 字段”。

#### 不建议直接照搬的部分

- `build_account_cookie()` 在每次运行前无条件补齐并写回配置：本项目已有“只在认证失败时刷新一次”的克制策略，避免无谓写盘与凭据扩散，不建议改成无条件补齐。
- `format_cookie()` 用 `";"` 连接、末尾加分号：本项目 `CookieJar::to_header()` 用 `"; "` 连接，两者都可被服务端接受，但不要为对齐上游而改动，以免引入无意义 diff。
- `x-rpc-lifecycle_id` 目前只有换票接口使用，其它请求不需要；不要扩散到全站请求头。
